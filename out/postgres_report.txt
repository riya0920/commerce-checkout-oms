SE-1 POSTGRES PASS
==============================================================================
PostgreSQL 17.2, loopback, fsync off.

THE CAVEAT THIS PROJECT CARRIED FOR FOUR PASSES:

  'SQLite, not Postgres, and no Postgres binary is installable in this
   environment. The conditional-UPDATE shape transfers; the throughput
   number does not.'

  The first clause is false. The official Windows x64 binaries are a
  297 MB zip that unpacks and runs initdb into a local directory -- no
  installer, no service registration, no administrator rights. It was
  written in the first pass and repeated three times without being
  retested. THAT IS THE SAME FAILURE THIS PORTFOLIO KEEPS FINDING IN
  OTHER PEOPLE'S NUMBERS: a caveat is a claim, and an unretested claim
  does not become true by being repeated.

READ THE ONE-SKU OPTIMISTIC ROWS AGAINST EACH OTHER.

    sqlite   :  640 of  640 granted,    40 retries
    postgres :  272 of  640 granted,   417 retries

  THE CAVEAT WAS UNDERSTATED. It said the throughput number does not
  transfer. What does not transfer is the BEHAVIOUR: on Postgres the
  optimistic mechanism starves 57% of requests that had stock
  available, and on SQLite the identical code starves 0%.

  The reason is not that SQLite is better. It is that SQLite SERIALISES
  WRITERS, so a compare-and-set has nothing to lose a race to: the
  version cannot move under a caller who holds the only write lock in
  the database. The optimistic mechanism's characteristic failure is
  INVISIBLE THERE BY CONSTRUCTION -- not smaller, invisible.

  Which means the previous benchmark was not a weak measurement of
  optimistic-vs-pessimistic concurrency. It was a measurement of
  something else that had been labelled with that name.

  Spreading the same workload over more rows fixes it:
      1 sku ->  272/ 640 granted ( 57.5% starved),   417 retries
      4 sku ->  591/ 640 granted (  7.7% starved),   880 retries
     16 sku ->  640/ 640 granted (  0.0% starved),   165 retries
     64 sku ->  640/ 640 granted (  0.0% starved),    97 retries

  That is the data-model question the old benchmark could not ask.
  Contention is a property of how many customers want the same SKU, and
  on SQLite it was indistinguishable from the engine's own serialisation.

ON THROUGHPUT, COMPARE THE PESSIMISTIC ROWS, NOT THE OPTIMISTIC ONES.

  Comparing rates on the optimistic hot row would be comparing a run
  that granted 640 requests against one that granted 272. The pessimistic
  rows are the like-for-like pair -- both grant everything:

    1 sku : sqlite    852/s   postgres    788/s
   16 sku : sqlite    972/s   postgres   1154/s

  Absolute rates on one machine are noisy enough that a single run
  flips the sign: consecutive runs gave Postgres 917/s then 563/s on
  the same cell. So the claim is made on the SHAPE, measured PAIRED --
  the one-row and sixteen-row cells run back to back within each
  repetition, so machine drift cancels instead of landing in the ratio.

  Throughput gain from spreading the same workload 1 row -> 16 rows,
  9 paired repetitions, pessimistic mechanism:

    sqlite   : median 0.86x   (range 0.37 - 1.41)
    postgres : median 1.33x   (range 1.17 - 1.54)

  Postgres scaled more than SQLite in 7 of 9 paired repetitions.

  SQLite's range includes 0.37 -- it sometimes goes SLOWER with more
  rows, which is what 'the number of distinct rows is irrelevant to
  this engine' looks like when you measure it: noise around 1.0. Its
  global write lock does not care how many rows there are. Postgres's
  row locks do.

  THAT IS SE-2'S PREDICTION, TESTED: 'writers on different rows queue
  here and would proceed in parallel on Postgres.'

  IT HOLDS IN DIRECTION AND NOT IN MAGNITUDE. The paired count -- 7 of
  9 -- is the part that reproduces; the median ratio itself moved from
  1.50x to 1.33x between two runs of this same nine-rep measurement.
  So: Postgres does benefit from spreading writers across rows and
  SQLite does not, which is the structural claim. 'Proceed in parallel'
  overstates the size -- at 16 workers the bottleneck is already partly
  the client, and no engine change moves that.

  A CORRECTION TO THIS PROJECT'S OWN FIRST POSTGRES RUN. The initial
  version of this harness started its timer before the worker threads
  connected, so ~4.8 s of Postgres connection setup was charged to the
  drill while SQLite's file-open cost nothing. It reported 452/s against
  32/s and I put that in the README. Timing now starts when the barrier
  trips and `setup_seconds` is reported separately.

B. THE RETRY BUDGET -- A DEFAULT CALIBRATED AGAINST THE WRONG ENGINE
==============================================================================
`reserve_optimistic` defaults to max_retries=8. Sixteen workers on ONE
row, ample stock:

 max_retries  granted  attempted  starved  starved_share  retries   seconds
           4      173        640      467          0.730      111     1.532
           8      281        640      359          0.561      480     2.585
          16      403        640      237          0.370     1074     3.014
          32      539        640      101          0.158     3084     4.476
          64      616        640       24          0.037     5921     5.966

  At the shipped default of 8, 56% of requests are refused with
  stock on the shelf. At 64 it is 4%, and the retry count has gone
  from 480 to 5921 to buy that.

  IT NEVER REACHES ZERO. Optimistic concurrency converts contention
  into wasted work, and the budget decides how much waste you buy the
  tail with -- it does not decide whether the tail exists. A hot row
  needs the pessimistic path or a different data model, and no retry
  number fixes it.

  The default of 8 was not chosen carelessly. It was chosen against a
  database where it was never tested, because SQLite cannot generate
  the contention that tests it.

==============================================================================
WHAT STILL DOES NOT TRANSFER
==============================================================================
  Client and server are one machine over loopback. No network, no
  serialisation across a wire, no connection pool, fsync off. These are
  a floor, exactly as the load generator's numbers are, and the engine
  change does not touch that.
